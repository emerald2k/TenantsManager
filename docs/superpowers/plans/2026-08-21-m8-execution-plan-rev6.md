# M8 — Execution plan, rev 6 · **ready to code**

**2026-08-21.** Supersedes rev 5. Requirements live in `SRS.md` **v4.6**, which is
the source of truth; this file holds the stage sequence, the gates, and what each
stage touches.

Rev 6 exists because rev 5 predates two things: the third wave of decisions
(deposit settlement, upward rounding, no write-off) and a consistency audit that
found **46 contradictions** in the SRS — including a balance formula that
subtracted `amountPaid` twice, and `roundingSurplus` declared on the wrong
collection. All are fixed. The SRS is internally consistent as of v4.6.

## 2. Stages

Each stage: verified by me, reported, **awaiting explicit approval before its
commit** (`CLAUDE.md` §2). New code ships with its own tests. Every stage also
gates on `npm run lint` and `npm run build`, which no band covers.

**Owner decision, 2026-08-30 — the gate widens for every stage from 15 onward.**
Each remaining stage closes with **all four bands run, not inferred**: fast
(`npm run test:run --prefix web`), rules (`npm run test:rules --prefix web`),
functions (`npm run test:emulator --prefix functions`) and **E2E**
(`npm run test:e2e` at the root). The per-stage Gate column below still says
_which_ band proves _what_ — that reasoning stays and is what the report must
answer. What changes is that a band is no longer skipped because the stage did
not touch it: a green suite that nobody ran proves nothing, and the four
regressions this milestone has already found were each in a band the stage
"did not touch". Practical constraints, both real: the three emulator bands and
E2E all bind **port 8080**, so they run **one after another, never in
parallel**; and E2E needs **port 5173 free**. If a port is held, free it and say
so in the report — do not report a band as passed when it did not start.

Roughly fourteen test files construct report IDs or route by property and will need the same treatment; the largest are `reports.hooks.test.jsx` and `reports.page.test.jsx`.

One piece of luck worth naming: **`web/tests/reportsInvoices.rules.test.js` already exists and tests exactly the thing that breaks** — the Storage rule resolving `/reports/{reportId}/invoices/*` back to a Firestore document. Extend it with a report whose attachments were migrated, and the gate for stage 4's worst failure is a test you already own.

**The seed is already drifted, independently of M8.** It writes no `reportReminderDaysBefore` at all, so M6's report-preparation reminder has never been exercisable against seeded data. Stage 4 is the moment to close that too, and to add `paymentReminderDaysBefore`, `roundingSurplus`, a terminated tenancy with a `depositSettlement` and a `closingBalance`, and a month in which a property changed hands — the case the whole re-keying exists for. `notifications` stays unseeded by design (FR-NLOG-08: the log starts empty).

**Measured, 2026-08-23 (`functions/scripts/probeProdShape.js` against production).**
4 `monthlyReports`, all `signed`, in **one** month; 4 `tenancies`; **3 invoice
objects in Storage**, every path matching the assumed `reports/{id}/invoices/{file}`
shape; **zero** reports missing `tenancyId`; **zero** new-ID collisions; **zero**
properties that have held more than one tenancy. The migration moves four
documents and three files — the maintenance window is seconds, not minutes.

Three things this does **not** license. **It is a snapshot, not a guarantee**:
production is live and the administrator keeps using it, so the probe is re-run
immediately before stage 20's migration and the numbers below are re-read, never
assumed. **The script still handles every case** — a missing `tenancyId`, a
collision, an unexpected path shape, a draft report, a month with two tenancies —
because the case that is absent today is the one that appears the week it is not
handled. And **the first run of this probe reported zero attachments**, because
it read `report.attachments`, a field that does not exist: attachments live per
cost line (FR-REP-03a). A verification that looks in the wrong place reports a
clean result for a database nobody has examined — `CLAUDE.md` §7's vacuity rule,
committed by the probe that existed to prevent exactly that.

**Stage 4 was written as the milestone's real risk, and it grew after rev 6 was first written.** `storage.rules` resolves invoice access with `firestore.get(monthlyReports/$(reportId))` on the id taken from the **Storage path**. Re-key the documents without moving the objects and every historical invoice becomes unreadable to the tenant — silently, as a permission denial, and invisibly to every band, because an emulator seeded after the migration is internally consistent. Hence two chained migrations, one of them over binary data, on production, with only a manual backup. If any stage in this plan deserves a rehearsal against a copy of production first, it is this one.

**Why this order.** Stage 2 precedes every new admin page — pinning `status`
exists to catch a stray write from a page that does not exist yet. Stage 3
precedes both migrations. Stage 4 is as early as it can be: it changes document
IDs, and everything after would otherwise be written against the old key. Stage 5
fixes the arithmetic before stage 15 renders it. Stage 9 sits adjacent to stage
8, which creates its hazard. Stage 14 needs stage 13's A8 to already exist, or
that template ships without `type`/`audience` and has to be retrofitted.

**One sequencing trap.** Stage 10's shared table must not enter
`ReportSummaryView`'s import tree without re-running stage 9's G1 — that
component is pinned light, and a shared table is by definition also used on
themed admin pages where `dark:` utilities are legitimate.
