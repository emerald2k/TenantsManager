**Stage 4 also owns the seed and the fixtures, and this is not optional.**
`functions/scripts/seed.js:497` builds report IDs as `` `${propertyId}_${year}-${MM}` ``, replicated locally on purpose. Re-key the documents and the seed produces data the application cannot find — **and the E2E band dies with it**, because `e2e/global-setup.js` spawns the seed as part of the band's own definition. Roughly fourteen test files construct report IDs or route by property and will need the same treatment; the largest are `reports.hooks.test.jsx` and `reports.page.test.jsx`.

One piece of luck worth naming: **`web/tests/reportsInvoices.rules.test.js` already exists and tests exactly the thing that breaks** — the Storage rule resolving `/reports/{reportId}/invoices/*` back to a Firestore document. Extend it with a report whose attachments were migrated, and the gate for stage 4's worst failure is a test you already own.

**The seed is already drifted, independently of M8.** It writes no `reportReminderDaysBefore` at all, so M6's report-preparation reminder has never been exercisable against seeded data. Stage 4 is the moment to close that too, and to add `paymentReminderDaysBefore`, `roundingSurplus`, a terminated tenancy with a `depositSettlement` and a `closingBalance`, and a month in which a property changed hands — the case the whole re-keying exists for. `notifications` stays unseeded by design (FR-NLOG-08: the log starts empty).

**Stage 4 is the milestone's real risk, and it grew after rev 6 was first written.** `storage.rules` resolves invoice access with `firestore.get(monthlyReports/$(reportId))` on the id taken from the **Storage path**. Re-key the documents without moving the objects and every historical invoice becomes unreadable to the tenant — silently, as a permission denial, and invisibly to every band, because an emulator seeded after the migration is internally consistent. Hence two chained migrations, one of them over binary data, on production, with only a manual backup. If any stage in this plan deserves a rehearsal against a copy of production first, it is this one.

**Why this order.** Stage 2 precedes every new admin page — pinning `status`
exists to catch a stray write from a page that does not exist yet. Stage 3
precedes both migrations. Stage 4 is as early as it can be: it changes document
IDs, and everything after would otherwise be written against the old key. Stage 5
fixes the arithmetic before stage 15 renders it. Stage 9 sits adjacent to stage
8, which creates its hazard. Stage 14 needs stage 13's A8 to already exist, or
that template ships without `type`/`audience` and has to be retrofitted.

**One sequencing trap.** Stage 10's shared table must not enter
`ReportSummaryView`'s import tree without re-running stage 9's G1 — that
component is pinned light, and a shared table is by definition also used on
themed admin pages where `dark:` utilities are legitimate.

## 3. Accepted risks — decisions, not oversights

Recorded in SRS §2.8 and §9. **No automated backup** (manual export, plus the
mandatory one before stage 4). The admin account keeps a 6-character minimum, no
2FA, no session expiry. `mail` is never purged, so generated passwords persist in
clear text. No second Google account owns the project, so losing the primary
account loses the project, the data and the billing. **`FR-SYS-05` and
`FR-SYS-06` are the compensating controls** — the product moves from no
detection at all to detection without prevention.
